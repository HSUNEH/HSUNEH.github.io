Merged a four-step LLM pipeline into one agent: tool selection 60% → 95%

An on-prem AI assistant for apartment households: residents control lights, heating, gas, the elevator and more by voice. I took it from a four-call LLM pipeline to a single agent, from design through production.

4단계 LLM 파이프라인을 단일 에이전트로 합쳐 툴 선택 정확도 60% → 95%

아파트 세대에서 조명·난방·가스·엘리베이터 등을 말로 제어하는 온프레미스 AI 비서입니다. LLM을 네 번 연달아 부르던 구조를 단일 에이전트로 바꾸고, 설계부터 프로덕션 배포까지 맡았습니다.

Problem문제

Four LLM calls for every request

Every request went through four LLM calls in a row: a tool classifier, a command check, the tool call, and a final answer.

  • Latency stacked up with every call.
  • A classification error in one step carried into the next, so the right tool was picked only 60% of the time.

요청 하나에 LLM 네 번

모든 요청이 툴 분류 → 명령 확인 → 툴 호출 → 답변 정리, 네 번의 LLM 호출을 차례로 거쳤습니다.

  • 호출할 때마다 응답 지연이 쌓였습니다.
  • 한 단계의 분류 오류가 다음 단계로 그대로 번져, 최종 툴 선택 정확도가 60%에 그쳤습니다.
Solution해결

What I changed바꾼 것

  1. One inference instead of four

    Rebuilt the pipeline as a single agent on a lightweight LLM served on-prem with vLLM. With OpenAI function calling, choosing a tool and calling it happen in the same inference.

  2. Tool descriptions as the main lever

    Rewrote the description and parameter schema of each of the 40+ tools, from lighting, heating, ventilation, gas and the elevator to weather and news. This prompt work is what moved tool-selection accuracy from 60% to 95%.

  3. Sessions per household

    Isolated sessions by household (building and unit number) and added TTL-based caching.

  4. Measure every change

    Defined quantitative evaluation metrics and built an automated evaluation pipeline, so every change was checked for quality.

  5. Plan for the next limit

    A single agent loses accuracy past about 15 tools, and new domains such as shopping would bloat the system prompt. I designed a staged move, from single agent to router plus specialist agents to orchestrator, that changes only how tools are grouped and leaves the tool code alone.

  1. 네 번 대신 한 번의 추론

    파이프라인을 온프레미스 vLLM으로 서빙하는 경량 LLM 기반 단일 에이전트로 다시 설계했습니다. OpenAI Function Calling으로 툴 선택과 실행을 한 번의 추론에서 처리합니다.

  2. 정확도를 올린 핵심, 도구 설명

    조명·난방·환기·가스·엘리베이터부터 날씨·뉴스까지 40여 개 도구의 description과 parameter schema를 하나하나 다시 설계했습니다. 이 프롬프트 작업으로 툴 선택 정확도가 60%에서 95%로 올랐습니다.

  3. 세대별 세션

    세대(동·호) 단위로 세션을 격리하고 TTL 기반 캐싱을 넣었습니다.

  4. 바꿀 때마다 측정

    정량 평가 지표를 정하고 자동 평가 파이프라인을 만들어, 수정할 때마다 품질을 검증했습니다.

  5. 다음 한계에 대비

    단일 에이전트는 도구가 15개를 넘으면 선택 정확도가 떨어지고, 쇼핑몰 같은 새 도메인이 붙으면 시스템 프롬프트가 비대해집니다. 기존 도구 코드는 그대로 두고 묶는 방식만 바꾸는 단계적 전환(단일 → 라우터+전문 에이전트 → 오케스트레이터)을 설계했습니다.

The single agent went to production and ran stably. On the same project, an arbitration server for 7 devices cut wrong-room wake-word replies from 50% to 10%, and chunked streaming TTS made responses 20% faster. Both became the team's standard architecture.
