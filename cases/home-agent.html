Architecture구조

Problem문제

An on-prem AI assistant for apartment households: residents control lights, heating, gas, the elevator and more by voice. To handle one request, the old design called the LLM four times in a row: tool classification, command check, tool call, then the final answer.

Each extra call added latency. Worse, when an early step classified wrong, every later step inherited the mistake. The right tool was picked only 60% of the time.

아파트 세대에서 조명·난방·가스·엘리베이터 같은 기능을 말로 제어하는 온프레미스 AI 비서입니다. 기존 구조는 요청 하나를 처리하려고 LLM을 네 번 차례로 불렀습니다. 툴 분류, 명령 확인, 툴 호출, 답변 정리 순서입니다.

호출이 늘어난 만큼 응답이 늦어졌습니다. 앞 단계에서 분류를 틀리면 뒤 단계가 그 오류를 그대로 이어받았고 최종 툴 선택 정확도는 60%에 머물렀습니다.

Solution해결

I collapsed the four steps into one. A lightweight LLM now runs on-prem with vLLM, and with OpenAI function calling it picks the tool and calls it in the same inference. With a single step there is no later step for an error to spill into.

Most of the accuracy came from the tools themselves. I rewrote the description and parameter schema of each of the 40+ tools, from lighting, heating, ventilation, gas and the elevator to weather and news. Sessions are isolated per household (building and unit number), with TTL-based caching.

To see whether each change actually helped, I defined quantitative evaluation metrics and built an automated evaluation pipeline that ran on every change.

네 단계를 하나로 합쳤습니다. 온프레미스 vLLM에 경량 LLM을 올리고 OpenAI Function Calling으로 툴 선택과 실행을 한 번의 추론에서 끝내도록 단일 에이전트를 다시 설계했습니다. 단계가 하나뿐이라 오류가 넘어갈 다음 단계도 없습니다.

정확도는 주로 도구 설명을 고치면서 올랐습니다. 조명·난방·환기·가스·엘리베이터부터 날씨·뉴스까지 40여 개 도구의 description과 parameter schema를 하나씩 다시 썼습니다. 세대(동·호)마다 세션을 나누고 TTL 기반 캐싱도 넣었습니다.

수정이 실제로 나아졌는지 확인하려고 정량 평가 지표를 정하고 자동 평가 파이프라인을 만들어 고칠 때마다 돌렸습니다.

The single agent shipped to production and ran stably. On the same project, a central arbitration server for 7 devices cut wrong-room wake-word replies from 50% to 10%, and chunked streaming TTS made responses 20% faster. Both became the team's standard architecture.

A single agent still loses accuracy past about 15 tools, and new domains such as shopping would bloat the system prompt. I planned a staged move for that: single agent, then a router with specialist agents, then an orchestrator. Only the way tools are grouped changes. The tool code stays as it is.

단일 에이전트는 프로덕션에 배포돼 안정적으로 운영됐습니다. 같은 프로젝트에서 기기 7대를 조율하는 중앙 승인 서버로 엉뚱한 방의 웨이크워드 응답을 50%에서 10%로 줄였고 청크 단위 스트리밍 TTS로 응답 속도를 20% 개선했습니다. 두 구조 모두 팀 표준 아키텍처로 채택됐습니다.

단일 에이전트도 도구가 15개를 넘으면 선택 정확도가 떨어지고 쇼핑몰 같은 새 도메인이 붙으면 시스템 프롬프트가 비대해집니다. 그래서 단일 에이전트에서 라우터와 전문 에이전트, 다시 오케스트레이터로 가는 단계적 전환을 설계해 두었습니다. 기존 도구 코드는 건드리지 않고 묶는 방식만 바꿉니다.
